# Carmen Business Web

A fast static storefront for selling **courses, books, guides, templates and bundles**, modelled on a shop-first author/coach site: the home page *is* the shop. Products live in a **Supabase database**, and a small build step publishes them as static, search-friendly pages ([ADR-0006](docs/adr/0006-catalogue-in-the-database-published-via-build-hook.md)).

| Feature | Where |
|---|---|
| Shop with search, price range, category filters, sort, pagination (filters live in the URL, so they are shareable) | `/` |
| Product pages, **pre-rendered** per product with a unique title, canonical URL and `Product`/`AggregateRating` JSON-LD; tabs (Description / Additional information / Reviews) and related products | `/product/<slug>/` |
| Cart drawer + cart page, discount-code preview, persistent across visits. One licence per product unless a product allows more ([ADR-0008](docs/adr/0008-digital-licence-quantity-fixed-at-1.md)) | all pages, `/cart.html` |
| Reviews page: rating summary, distribution bars, search, sort, pagination | `/reviews.html` |
| Free resources / lead magnets, About, Contact, Terms, Privacy, 404 | `/free.html` … `/404.html` |
| "10% off your first order" newsletter popup that applies the code in the cart | `popup` in config |
| `sitemap.xml`, `robots.txt`; old `product.html?id=` links 301-redirect | generated by the build |
| Dark mode, mobile menu, skip link, keyboard-accessible tabs/dialogs, reduced motion | everywhere |

> **Payments:** the store will take payments through **Payfast in rands (ZAR)** ([ADR-0009](docs/adr/0009-payfast-gateway-and-zar.md)). That arrives in PR 3. Until then, "Go to checkout" lets a customer email their order. The old Stripe prototype has been removed.

## 1. Edit content and products

- **Products** (title, price, description, images, categories, bundles) live in the database. Until the admin screens arrive (PR 9), edit them in Supabase. Locally, `supabase/seed.sql` holds the sample catalogue. After a change, run `npm run build` (in production, the admin's "Publish" button will trigger the build). Checkout always re-prices from the database, so the prices shown on a page are display-only.
- **Site content** is in **`assets/js/site-config.js`**: brand, announcement bar, nav, shop intro, reviews, free resources, about text, popup. A review's `productId` must be a published product slug, or the build fails. Only reviews with `verified: true` show a "Verified buyer" badge.
- **Product images:** set `images` on a product to `[{ "src": "/assets/img/my-course.webp", "alt": "…", "width": 1200, "height": 800 }]` (optional `srcset`). Without one, a generated cover is drawn from `display.color`.
- **Re-brand** by editing the `:root` tokens at the top of `assets/css/styles.css` (`--brand` is the accent colour) and the logo text/script font.

Placeholder copy, prices and reviews **must be replaced** with the client's real content before launch, and the Terms/Privacy templates reviewed by a professional.

## 2. Forms

Set `brand.formEndpoint` to a Formspree/Basin/ConvertKit-style endpoint that accepts a JSON POST (`{name, email, message}`). Blank = forms open the visitor's email app addressed to `brand.email`.

## 3. Develop, test, deploy

Requires Node 22.18+ (`.nvmrc`; scripts run as TypeScript natively) and Docker (for the local database). Dependencies are pinned exactly and locked.

```bash
npm ci                 # install the exact locked toolchain
npm run db:start       # local Supabase: migrations + sample catalogue
npm start              # build dist/ from the database, serve http://localhost:8080
npm run typecheck      # strict TypeScript for scripts and server code (ADR-0002)
npm test               # unit, build, content/link and repo guard-rail tests (no database needed)
npm run test:db        # schema lint + pgTAP (RLS matrix, integrity) + API-surface tests
npm run build          # dist/ from the database (needs SUPABASE_URL/ANON_KEY, or the local stack)
npm run test:build     # build output: no private data, catalogue matches the database
npm run test:e2e       # Playwright browser scenarios against dist/
npm run check          # all of the above
```

`SHOTS=/some/dir npm run test:e2e` also saves full-page screenshots at desktop and mobile widths. On a fresh machine, run `npx playwright install chromium` once.

**Deploying (Netlify):** `netlify.toml` builds with `npm run build` and publishes `dist/`. The site needs `SUPABASE_URL` and `SUPABASE_ANON_KEY` (the public key; RLS restricts it to published products) in the Netlify environment. Netlify sets `URL`, which becomes the canonical origin; `SITE_URL` overrides it. A failed build leaves the previous deploy live.

The schema, access rules and their tests are documented in [`docs/database.md`](docs/database.md).

### Continuous integration

Every pull request, and every push to `main` or `staging`, runs `.github/workflows/ci.yml`. Any red job blocks merge once branch protection is enabled.

| Job | Gate |
|---|---|
| Typecheck, unit tests, audit | `tsc`, `node:test` suites, `npm audit --audit-level=high` |
| End-to-end | Fresh local Supabase → build from the database → build-output leak and consistency checks → Playwright on Chromium (screenshots uploaded as an artifact) |
| Secret scanning | gitleaks over the **full git history** (binary checksum-verified) |
| Database | Fresh local Supabase: migrations + seed from scratch, schema lint, pgTAP, API-surface tests, generated-types drift check |

Actions are pinned to commit SHAs, and Dependabot proposes updates weekly (npm) and monthly (actions). Secrets never go in the repo: `.env.example` lists every variable, and real values live only in Netlify environment settings, separate for test and live.

### Branches and pull requests

`main` is the protected base, `staging` deploys to the staging context in payment test mode, and each backlog item gets its own `feat/<nn>-<slug>` branch. Every PR uses `.github/pull_request_template.md`, including an **Acceptance evidence** table. Plans and decisions are in [`docs/`](docs/), with ADRs in [`docs/adr/`](docs/adr/).

```

assets/css/styles.css      design tokens + styles
assets/js/site-config.js   site content (brand, copy, reviews, popup); no products
assets/js/lib.js           pure logic: filtering, cart maths, reviews, URL safety (unit-tested)
assets/js/render.js        HTML templates shared by the browser and the build
assets/js/main.js          page behaviour + interactions
scripts/build.mts          database → dist/ (catalog.js, product pages, sitemap, robots)
tests/                     unit (site, build, repo), build output, database API, e2e; fixtures/
supabase/                  config, migrations, seed, pgTAP tests, rollback scripts
types/database.ts          generated DB types
docs/                      architecture review, backlog, database, ADRs
.github/                   CI workflow, Dependabot, PR template
```

## Design notes and trade-offs

- Product pages are pre-rendered at build time for search engines and no-JS clients; the browser then re-renders the same markup from the same templates (`render.js`) and adds interactivity.
- Cart contents and the discount code live in the visitor's `localStorage`. The popup's code is public by design (a first-order incentive). What is actually charged will be decided only by the server (PR 3).
- All database and config text is HTML-escaped in both the browser and the build. Image and social URLs are restricted to `http(s)` or relative links, and generated JSON can't break out of its `<script>` tag.
